# Intent: elevate's policy kernel

elevate is built proof-first. The rules that decide whether an agent swarm may touch your repositories are written down here first, stated as a formal spec in Verus (`verified/src/lib.rs`), and proved for every input. The TypeScript that the app runs (`packages/policy`) is then compared with the proved code over every input class. `RECEIPT.md` records what was proved and checked, and it is regenerated by `node proof/run.mjs`.

The method follows [PDD Kit](https://www.microsoft.com/en-us/research/blog/formally-verifying-agent-written-full-stack-web-apps-with-pdd-kit/):

1. **Intent first.** This file states the requirements in the product's own words. It also has a decision card wherever the words leave a choice open.
2. **A spec in Verus.** Each clause has a plain-English comment and a tag (`// L4`, `// W3`, and so on) that matches a requirement below.
3. **A proof** that the code meets the spec for every input.
4. **A mutation check** (`mutation-check.mjs`). One bug is planted per clause, and Verus must reject each on the clause it targets.
5. **Trusted pieces are named**, and each has a check: the differential test D, its negative control, and the unit tests.
6. **A receipt** (`RECEIPT.md`) that marks every requirement as proved or checked.

## Scope

These are the four pure decisions that stand between a headline on the internet and a branch on your repo. All four live in `packages/policy/src`.

| Decision | TypeScript | What a bug would do |
|---|---|---|
| Gate 1, legitimacy | `legitimacyDecision` | Hype reaches your inbox looking verified. |
| Gate 2, soundness and impact | `soundnessDecision`, `recommendationScore` | A change that won't make a difference, or can't be measured, gets proposed. |
| The recommendation lifecycle | `transition` | A swarm starts on something you never approved, or that never passed the gates. |
| The write guard | `authorizeWrite` | An agent writes to a repo you didn't allow, merges, or overspends. |

These are not in scope, and are covered elsewhere or not at all:

- **The quality of the inputs.** The LLM's review scores, the heuristic evidence prior, relevance, and how risky a change is are all produced by models and heuristics, and nothing here proves they are right. The kernel promises only what is done with them. The gate eval set (`fixtures/gate-eval.json`, run with `pnpm eval:gates`) is the evidence for input quality.
- **The GitHub calls themselves.** The guard decides, and the executors must ask it before every write. That every write goes through `authorizeWrite` is trusted piece TB3, enforced by one choke point: `guardedGitHub` in `packages/executors`.

## Requirements

### Gate 1: "the new thing is actually legit"

Inputs (each normalized to an integer from 0 to 100):

- `prior`: the evidence-weighted heuristic. It combines source credibility, corroboration across independent sources, community signal, public code and cited evidence.
- `review`: the skeptical LLM reviewer's score.
- `legit`: the reviewer's verdict.
- `threshold` and `priorFloor`: both come from settings.

| # | Requirement | Spec |
|---|---|---|
| L1 | The legitimacy score is `(2·prior + 3·review) / 5`, rounded down. The reviewer reads the evidence, so it weighs more, but neither input decides alone. | `combined` exact |
| L2 | The score stays between 0 and 100. | bounded |
| L3 | More evidence never hurts. Raising the prior or the review never lowers the score and never turns a pass into a fail. | monotone |
| L4 | The reviewer can veto. A technique the reviewer calls not legit never passes, whatever the evidence says. | veto |
| L5 | The model alone can't pass anything. A technique whose independent evidence is below the floor never passes, however much the reviewer likes it. | floor |
| L6 | Otherwise it passes when the score reaches the threshold, and only then. | exact iff |

### Gate 2: "the improvement is sound and will make a difference"

| # | Requirement | Spec |
|---|---|---|
| S1 | Nothing is judged sound for a technique that failed Gate 1. | prerequisite |
| S2 | The reviewer can veto. A change it calls unsound never passes. | veto |
| S3 | "Will make a difference" must be checkable. A change with no stated way to measure its impact never passes. | measurable |
| S4 | Riskier changes need a stronger case. The bar is the threshold plus 0, 5 or 15 for low, medium or high risk (decision D2), capped at 100. A score that passes at high risk passes at medium, and one that passes at medium passes at low. | margin, monotone in risk |
| S5 | Otherwise it passes when the score reaches the bar, and only then. | exact iff |
| S6 | The inbox rank is `(30·relevance + 30·legitimacy + 40·soundness) / 100`, rounded down. It stays between 0 and 100 and never drops when any input rises. | rank exact, bounded, monotone |

### The lifecycle: "launches a swarm upon approval after verifying"

The statuses are `candidate`, `gated_out`, `open`, `approved`, `rejected`, `in_progress`, `pr_opened` and `failed`. The events are `gate_pass`, `gate_fail`, `approve`, `reject`, `start`, `pr`, `fail`, `retry`, `regate` and `reopen`.

| # | Requirement | Spec |
|---|---|---|
| T1 | Only an open recommendation can be approved. The one other way into `approved` is retrying a failed run, which you approved before. | into approved |
| T2 | A swarm starts only from `approved`. | into in_progress |
| T3 | Nothing reaches your inbox (`open`) without passing both gates. | into open |
| T4 | A recommendation filtered out by the gates can only go back to `candidate`, to be checked again. It can't be approved or started from there. | gated_out exits |
| T5 | A draft PR is the end: `pr_opened` has no way out. | terminal |
| T6 | A rejected recommendation reopens as a `candidate`, so it is re-gated against today's evidence rather than going straight back to your inbox. | reopen |
| T7 | **No swarm without both gates and your approval.** For every sequence of events from `candidate`, if the recommendation ends in `approved`, `in_progress`, `pr_opened` or `failed`, the sequence contains a `gate_pass`, and an `approve` that comes after it. | proved by induction over every event sequence |

### The write guard: "upon approval"

The actions are `create_issue`, `comment`, `assign_agent`, `run_local_agent`, `push_branch`, `open_pr`, `merge_pr`, `push_default_branch` and `force_push`. The guard answers `allow` or a single reason for refusing.

| # | Requirement | Spec |
|---|---|---|
| W1 | elevate never merges, never pushes to the default branch, and never force-pushes, whatever else holds. Those requests are refused as `forbidden`. | forbidden |
| W2 | No write happens until you approve. The recommendation must be `approved` or `in_progress`. | approval |
| W3 | Only repos you opted in (`allowSwarm`) are written to. | allow-list |
| W4 | A swarm writes only to its own recommendation's repo. | same repo |
| W5 | Pull requests are drafts. A non-draft `open_pr` is refused. | draft only |
| W6 | Spending stops at the budget. An action that starts agent work (`assign_agent`, `run_local_agent`) is refused once tasks, minutes or agent turns reach their limit. Publishing finished work (issue, comment, push to the swarm branch, draft PR) is still allowed (decision D3). | budget |
| W7 | Otherwise the write is allowed, and only then. | exact iff |

## Trusted pieces, and how each is checked

- **TB1. The WASM shim.** `*_code` functions sit outside `verus!` and turn integer codes into enums and back.
  - *Check:* D, the differential test, and its negative control.
- **TB2. The TypeScript is the code that runs.** The app runs `packages/policy`, not the WASM (decision D1).
  - *Check:* D compares them on every input class. Gate inputs are exhaustive over the score grid at the threshold boundaries. The lifecycle covers all 80 status and event pairs. The guard covers every action and status at the budget boundaries. Random sampling covers the rest of the domain.
  - *Check that D can fail:* the negative control runs D against mutant MW2, which drops the approval check, built to WASM. D must fail.
- **TB3. Every GitHub write goes through the guard.**
  - *Check:* `guardedGitHub` is the only GitHub writer that executors receive. A unit test runs a fake executor against a guard that refuses everything and asserts that no write reaches the fake GitHub.
- **TB4. Normalization.** `pct()` clamps a value to 0–100, rounds it, and maps anything that isn't finite to 0.
  - *Check:* unit tests.
- **TB5. The toolchain.** Verus, Z3, vstd and rustc are assumed correct, as PDD Kit assumes them.
- **TB6. The intent.** Turning these words into clauses is a human judgment. The mutation check catches a clause that rules out nothing, but it can't catch a clause that rules out the wrong thing. Your review of this file, and of the decisions below, is the check.

## Decisions (made, open to revision)

- **D1. How the proved code reaches the app.** We keep the TypeScript and gate CI on the proof plus D (recommended, and the choice in the PDD prototype). The domain is finite at its boundaries, so D covers every input class. The alternative is to ship the WASM.
- **D2. Risk margins.** The margins are 0, 5 and 15 for low, medium and high risk. They are applied on top of the soundness threshold, which defaults to 65. The alternative is a single bar for every risk level.
- **D3. What the budget stops.** The budget stops new agent work only. Pushing, commenting and opening the draft PR stay allowed, so a swarm that hits its limit can still hand you what it built. The alternative is to stop every write.
- **D4. Reopen.** A reopened recommendation is re-gated (T6) instead of returning straight to `open`.
- **D5. Threshold defaults.** The defaults are legitimacy 60, prior floor 30, and soundness 65. They are tuned against `fixtures/gate-eval.json` and stored in settings.
